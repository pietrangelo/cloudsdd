# RFC 009: Global State Tracking for Context-Aware AI

## 1. Context and Problem Statement
Currently, the `cloudsdd` CLI treats every natural language prompt as an isolated event. The AI translates the prompt into an SDD specification and the engine deploys it. However, if a user later says, *"create a resource in account X and allow it to be reached from the database in account Y"*, the AI has no memory of the database in account Y. 

To support advanced cross-account, cross-resource relationships and iterative infrastructure evolution, the CLI (and by extension the AI) needs to be aware of the "current state of the world".

## 2. Proposed Architecture

Rather than setting up a complex external database, we will leverage the concept of a **Global State Ledger** stored locally (similar to how Terraform/Pulumi store state, but strictly for the AI's contextual understanding).

### 2.1 The Global Ledger (`~/.cloudsdd/ledger.json`)
We will create a lightweight local registry that records every successfully deployed resource across all accounts. 
Since the SDD Specification is the ultimate source of truth (as per RFC 001), our ledger will simply be an aggregated collection of `spec.Resource` objects.

```json
{
  "last_updated": "2026-08-01T10:00:00Z",
  "resources": [
    {
       "id": "my-database",
       "type": "relational_database",
       "provider": "aws",
       "account": "account-y",
       "properties": { ... }
    }
  ]
}
```

### 2.2 CLI Integration
1. **Context Injection**: When the user runs `cloudsdd deploy "<prompt>"`, the CLI will read `ledger.json` and inject it into the Anthropic system prompt as:
   *`"Here is the currently deployed infrastructure. Use this context to resolve references: {ledger_json}"`*
2. **State Updates**: 
   - After a successful `engine.Apply()`, the CLI updates the ledger, adding or overwriting the deployed resources based on their `ID`.
   - After a successful `engine.Destroy()`, the CLI removes the targeted resources from the ledger.

### 2.3 System Design
- Create `internal/state/ledger.go` to handle reading/writing the JSON file securely (with file locking to prevent corruption).
- Update `internal/nlp/anthropic.go` to accept the ledger data and append it to the system prompt.
- Update `cmd/cloudsdd/deploy.go` and `destroy.go` to synchronize the ledger post-execution.

## 3. Security Considerations
- **No Secrets in Ledger**: The ledger only stores the SDD Spec (the declarative *intent*). It will not store runtime secrets (like the autogenerated RDS passwords), which safely remain inside the encrypted Pulumi state backend.
- **Local Isolation**: The ledger is stored in the user's secure home directory (`0700` permissions), maintaining the CLI's decentralized security posture.
