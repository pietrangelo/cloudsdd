# CloudSDD Implementation Plan: RFC 020 (Scope-Owned Filesystems) + carried-over documentation

Ordered per [RFC 020](docs/rfc/020-scope-owned-filesystems.md) §6, which
front-loads the seam: steps 1–4 change no behaviour, and the first
filesystem appears only in Phase 2. That split is deliberate — it keeps the
`CloudProvider` interface change reviewable on its own instead of arriving
inside the first provider that needed it, which is the mistake RFC 019 §1
was written to stop repeating.

**Already complete and not repeated here:** RFC 019 end to end, RFC 018's
Azure provider, and the Volumes data model in `internal/spec` (the `Volume`
struct, `Resource.Volumes`, the `mountpath` validator and
`validateVolumes`). That record lives in `docs/rfc/018-build-pipeline.md`,
`docs/rfc/019-rosette-consolidation.md`, and in the git history of this
file.

Items are ordered tests-first per `<todo_policy>`, which means a test item
may leave its package not compiling until the implementation item that
follows it. Every **implementation** item must leave the tree compiling and
`go test ./... -count=1` green.

RFC 020 §5's rule on existing tests: no assertion changes, with exactly two
exceptions, both of which are decisions this RFC took rather than drift —
the `build_pipeline` row in `TestValidateVolumes` moves groups (§2.4), and
the four fakes take the new `EnsureNetwork`/`DestroyNetwork` signature. A
third test needing a changed expectation means this RFC moved behaviour it
did not intend to.
